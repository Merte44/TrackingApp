## Bugs
### BUG-1 — Retry nach fehlgeschlagenem Migrationslauf nutzt die alte Verbindung weiter — High — Backend
- Repro (Code-Pfad `lib/db/index.ts` `doInit`, `lib/db/migrate.ts` `restoreForeignKeys`):
  1. Alle Migrationen committen, danach scheitert `PRAGMA foreign_keys = ON` bzw. dessen Prüfung → `migration_failed`, Verbindung bleibt offen
  2. „Erneut versuchen" → `runMigrations` sieht `from === latest`, meldet Erfolg, `ready = true`
  3. Erwartet: Foreign Keys an. Tatsächlich: App läuft mit `foreign_keys = OFF`, verwaiste Fremdschlüssel werden still gespeichert
- Verwandt: bleibt die Verbindung nach einem fehlgeschlagenen ROLLBACK in einer Transaktion hängen, scheitert jeder Retry mit „cannot start a transaction within a transaction", bis die App beendet wird — die Verbindung wird nur bei `version_read_failed` verworfen
- Fix-Richtung: nach **jedem** Fehler von `initDatabase` die Verbindung schließen und verwerfen, damit der Retry frisch öffnet (Pragmas neu gesetzt). Test: Restore-Fehlschlag → Retry → `foreign_keys = 1`
- Beleg: /code-review-Findings 1 + 2, Code gelesen

## Bugs
### BUG-2 — Retry kann trotz Fix die alte Verbindung zurückbekommen — High — Backend
- `expo-sqlite` cacht native Verbindungen pro Pfad (`node_modules/expo-sqlite/ios/SQLiteModule.swift:108`, `useNewConnection` = false). `dropConnection` verschluckt Fehler von `close()`; scheitert das Schließen, liefert `openExpoDatabase()` beim Retry dieselbe Verbindung (offene Transaktion, `foreign_keys = OFF`) zurück
- Der Weg „Datenbank aktuell" (`from === latest` in `runMigrations`) prüft `foreign_keys` nicht — damit startet die App auf einer solchen Verbindung still mit ausgeschalteten Foreign Keys
- Beleg: Finding 1 + 8, Quelltext expo-sqlite gelesen. Der Test aus Runde 1 deckt das nicht ab (Mock setzt die Pragmas selbst)

### BUG-3 — Falscher Nutzertext, wenn nur das Wiedereinschalten der Foreign Keys scheitert — Medium — Backend
- Migrationen sind committet (`user_version` hochgesetzt), danach scheitert `PRAGMA foreign_keys = ON` → Hinweis „Deine Daten sind unverändert" stimmt nicht
- Beleg: Finding 2, reproduziert durch den neuen Test aus Runde 1

## Befund (kein Bug): Rettungsmechanik
Der Fix aus Runde 1 rettet den Zustand an der falschen Stelle (Verbindung verwerfen in `index.ts`). Die Invariante „Foreign Keys an" gehört an das Ende **jedes** Init-Laufs bzw. in `openExpoDatabase` — unabhängig davon, ob Migrationen liefen. Weitere Findings dazu: Schließen auch bei gesunder Verbindung (`newer_than_app`), `await close()` kann hinter einem hängenden Aufruf blockieren, `ready`/`db` als doppelte Wahrheit.
